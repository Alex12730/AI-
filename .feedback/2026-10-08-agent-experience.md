# 本次实现反馈记录

## 已遇到的摩擦点

- 项目初始目录为空且尚未初始化 Git，需要先建立规格、计划和基础工程。
- 系统 PATH 没有 Python，但 Codex 工作区依赖提供了 Python 3.12；后续使用固定绝对路径，避免误报“缺少 Python”。
- Impeccable 前端上下文引擎未安装，默认缓存目录不可写且首次安装需要网络，因此无法运行随机概念生成器。本次依据用户已确认的产品流程建立保守的 Operate 界面，并在最终验收中单独检查可用性。
- 当前没有模型权重和 A6000 基准环境；软件接入与准入门槛可以实现，真实性能数据必须留给目标工作站实测，不能伪造。
- 新仓库首次提交因缺少 Git 作者身份失败。处理方式是仅为本仓库设置 `Codex <codex@local.invalid>`，不污染用户全局配置。
- Superpowers 的 `sdd-workspace` 脚本在本机 Git Bash 中找不到 `basename`，脚本没有建立台账。已按脚本公开的目录和首行格式手工建立等价台账。
- pip 的隔离构建在受限网络中两次卡住；改为先在项目 `.venv` 安装 `setuptools`/`wheel`，再使用 `--no-build-isolation` 做可编辑安装。启动脚本已固化这个顺序。
- 最终代码审查发现原 Worker 在模型推理期间持有 SQLite 写事务、CSRF 只生成未校验、模型重新配置后旧准入档仍有效等关键问题。已用失败测试逐项复现，再加入短事务租约、心跳令牌、CSRF 校验、配置指纹和媒体质检。
- 一次测试命令误用了系统 `python`，而本机 PATH 没有该命令；随后统一改用项目 `.venv\Scripts\python.exe`。后续自动化不应依赖裸 `python`。
- 登录回归测试最初跟随 303 重定向，导致读不到初始响应里的 CSRF 响应头；测试改为禁止自动跟随跳转，明确验证登录边界。

## 改进建议

- 为项目固定一个受控 Python 虚拟环境，并把启动脚本绑定到该解释器。
- 模型安装与平台代码分开验收：先用 Demo 适配器验证状态机，再逐个启用真实 Profile。
- 将“应用层拒绝外部 URL”和“操作系统阻断公网出站”拆成两层验收；只有两层都通过才能声称离线生产。
- 后续把当前管理 API 补成可视化管理页，尤其是账号授权、任务重试和验收签字，减少管理员依赖 Swagger/脚本。
- 前端设计工具若要使用，应把引擎缓存配置到可写工作区或预先安装，避免实现中途联网。

## 最终代理体验复盘

- 用户方案同时包含“软件实现”和“硬件/大模型实测”。代码仓库能够交付平台、适配器和准入工具，但无法在没有权重与目标工作站运行证据时诚实宣称 H3/Wan/LTX 已通过。README 和验收清单已把两类完成状态分开。
- Git 沙箱账户与提升权限账户不同，导致仓库出现 dubious ownership；每次提交使用精确的临时 `safe.directory`，没有修改全局配置。更理想的环境应让同一身份创建和提交仓库。
- Impeccable 引擎不可用时，仍通过真实浏览器检查发现并修复了模型页移动端整页横向溢出；说明 DOM 测试不能替代视觉验收。后续可在 CI 加入 390px/1280px 截图回归。
- FastAPI TestClient 当前发出 Starlette 的 httpx 弃用提示，测试仍通过。后续依赖升级时应按 Starlette 建议切换到 httpx2 或其新测试客户端，不应为消除提示而盲目固定旧版本。
- 辅助工具失败均有明确替代路径，但 `sdd-workspace` 对 Windows Git Bash 的 PATH 假设较强，建议脚本自带 `basename`/`dirname` 的 shell 参数展开兜底。

## 本次未冒进的边界

- 未下载数十 GB 模型权重，未伪造显存、速度、温度或成功率数据。
- 未开放 H3 未验证时长，未接入 Context-IR、Regenerate-2K 或任何云端视频生成服务。
- 未把演示账号、密码、会话密钥或本地测试数据库提交到 Git。
- 未修改 Windows 防火墙、Defender、更新策略、BIOS 或全局 Git 配置。

## 管理员初始化补充复盘

- 首次管理员最初依赖交互式 CLI，终端密码不回显让用户误以为无法输入；随后两次 PowerShell/WinForms 弹窗尝试也没有形成可靠的错误回传。连续失败后改为浏览器内的一次性 `/setup` 流程，复用了现有 Argon2、CSRF 和审计逻辑。
- 在 `/setup` 尚未实现时就先把地址交给用户，导致用户实际看到 `404 Not Found`。后续凡是给出可访问链接，必须先完成代码、启动服务并读取 HTTP 状态和页面标志，再交付给用户。
- 新版服务第一次启动时，旧 Python 进程仍占用 8000 端口；只检查新进程 PID 不足以证明替换成功。后续应同时检查端口监听 PID、HTTP 路由和启动日志，并在权限不足时只对已核实的精确 PID 请求提升权限。
- 图片识别辅助工具因本机视觉模型密钥返回 `401 invalid_api_key`，因此没有把失败结果当作截图证据；本次改用本地 HTTP 复现确认 404。后续需先修复视觉工具配置，且不得打印或提交密钥。
- 一次 SQLite 只读核验命令因 PowerShell 内嵌 SQL 引号解析失败，随后改为参数化查询。Windows 命令应优先避免嵌套同类引号，并继续坚持不输出密码哈希或会话密钥。

### 后续改进

- 首次启动流程应默认引导到网页初始化，CLI 仅作为无界面环境的备用方案。
- 服务重启验收至少包含：新路由状态、关键页面内容、端口监听 PID 和数据库状态四项，不再仅依赖健康检查。
- 用户正在浏览旧错误页时，应明确提示刷新或重新打开链接；不能假定后台代码更新会自动刷新现有标签页。
